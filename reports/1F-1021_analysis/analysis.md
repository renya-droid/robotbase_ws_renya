# 1F-1021：171〜300秒の経路追従解析

対象: `/home/ren/bag/1F-1021_0_fixed.mcap`。
時間は先頭メッセージ `2026-10-21 19:22:58.726381962 JST` を0秒とする。
修復済みファイルの末尾は約520.7秒であり、解析区間は切断箇所から離れている。

結論は、171〜270秒の主な問題が「経路の曲がり始めと車体の向きが合わず、前進・停止・後退を繰り返す」状態だったこと。
経路表示だけでは、追従処理が稼働中であることや、その向きから実際に走行できることは確認できない。
288〜302秒には、障害物への接近が疑われる別の停止・後退もある。

詰まっている間は、経路の最初の部分が車体から見て横〜後方にある。
図上では回り込む経路が存在していても、前進しながらその線へ入ることは難しい。
先に向き直る、適切に後退して入り直す、といった姿勢の調整が必要な形になっている。
手動操作後は経路自体も更新されており、手動旋回だけで改善したとまでは断定しない。

## 他の原因との照合

- `/cmd_vel_direct` の入力は171〜300秒にない。手動入力は270.8秒以降で、最初の約100秒の往復の原因ではない。
- `/stop` の記録は387.1秒のfalseのみ。この区間にstopの切り替えは記録されていない。ただし記録開始前のラッチ状態までは分からない。
- `/cmd_vel` とオドメトリは前進・後退の符号と開始・終了が概ね対応する。指令が来ているのに駆動系が継続して動かない、という状態が主ではない。
- オドメトリ・IMUは継続して記録されている。Nav2の速度指令の空白をbag全体の欠落として説明する証拠はない。
- 171〜270秒にTFの更新が車体のmap位置へ与える補正量は最大約3.4cm。`map→odom` のtranslation単体の変化は、遠方のodom原点に対するyaw補正も含むため、車体の位置飛びとして扱わない。
- ローカルコストマップの複数標本では、171〜270秒に車体が常時障害物セルへ重なっているわけではない。ただし約257.5秒の標本では経路近傍に高コストがある。環境要因や一時的な衝突判定を完全に除外するものではない。

## 有力な原因と確認の優先順位

最有力なのは、大きい方位差を含むグローバル経路に対して、追従側が向き直りを完了できず、
短い前進と後退の復帰を繰り返したこと。後退は主因そのものではなく、追従に失敗した後の動作と考えられる。

現在の `params/real/nav2.yaml` は NavfnPlanner と直接MPPIを組み合わせ、
`PreferForwardCritic.cost_weight=40`、`VelocityDeadbandCritic.cost_weight=35`、
予測時間2.8秒を設定している。現在のBTはSpin復帰を省いている。
前進を優先する評価と低い前進速度へのペナルティが、向き直りの選択を難しくしていないかが確認対象。
**これらは現在のファイルであり、収録時の実効パラメータを確認できたわけではない。重みが直接の原因とは断定しない。**

1. 収録時の実効パラメータ・使用BTを取得し、同じ曲がり始めで姿勢を合わせる制御が働くか確認する。
2. 大きい方位差があるときの姿勢合わせ（例: Rotation Shim）とMPPI単体の結果を比較する。車体外形による衝突確認を維持して行う。
3. その後に前進優先・低速ペナルティ・予測時間を比較する。障害物コストを一括で下げる対応は、この記録だけでは根拠が足りない。
4. 288〜302秒は別に、ローカルコストマップと車体外形で前方の衝突余裕を確認する。

次回は `/rosout`、FollowPath/Navigateのstatus・feedback、
`/cmd_vel_smoothed`、`/optimal_trajectory`、`/hokuyo_scan`、実効パラメータも保存すると、
MPPIの有効軌道なし・進捗不足・衝突判定・目標変更を区別しやすい。
